- Read before writing: blank (2048 × FFh). Note: minipro's pin-contact test (`-z`) is not supported on the T48.
- Wrote `rom/dumps/K573RF5_boot80k_original.bin`. minipro verify OK; readback MD5 `c79c66140c44dc0346a823e96a31f0e2`, identical to the РФ5. Also verified at VCC 4.5 V.

- **Interpretation:** the 80K boot's first actions are an LDIR of 00h over C000–DAFF (black screen) and then `OUT (FEh),40h` (black border). Neither happened, so **the CPU is not executing the boot ROM** (or its video writes and the 8255 both fail, which is less likely). Combined with the no-ROM /M1 period of 10 T (CPU reading non-FFh at its fetch addresses), the leading suspect is the **memory-configuration flip-flop U36 / NPOR**: if PO ≠ 1 at startup, NPO (boot /CE) is high and 0000h maps to DRAM. Also possible: boot /OE (NOEB, U56/3) not reaching the socket.
- Next: measure boot ROM /CE (chip pin 18 = socket pin 20) and /OE (chip pin 20 = socket pin 22).
- Boot ROM **/CE (chip pin 18, socket 20 = NPO)**: **steady LOW, 0.19 V avg** (−0.36…0.56 V noise) (`20261105-164014_boot-CE-pin18-low.png`). NPO = 0, so PO = 1, so U36 is in the startup config and the chip is enabled. ✅ The U36/NPOR theory is weakened.
- Boot ROM **/OE (chip pin 20, socket 22 = NOEB from U56/3)**: **stuck HIGH, 3.80 V** (3.52–4.00 V), no pulses in a 24 µs window (`20261105-164110_boot-OE-pin20-stuck-high.png`). **Right now the CPU is not reading 0000–3FFF at all.** A running boot ROM would keep /OE pulsing forever (LDIR clear, then the logo loop), so the CPU is executing somewhere else. Two cases: (a) /OE pulses briefly at power-up and the CPU then runs away (bad data reaching the CPU); (b) /OE never pulses (NOEB decode U56 / trace fault). Next: power-up capture with a falling-edge trigger on /OE.

- Second power-up capture (240 ms window) is **invalid**: the probe slipped off /OE during the capture. Its pre-trigger part also shows ~3.8 V, i.e. something was powered before switch-on. Discarded (`20261105-164634_boot-OE-powerup-INVALID-probe-slipped.png` kept for the record).
- **Valid power-up capture of /OE** (probe tip held by hand, 240 ms window, 12 Mpts @ 40 ns; export `acquisition-53rgbyqk`, not committed; `20261105-164948_boot-OE-powerup-240ms.png`, zoom `20261105-165114_boot-OE-powerup-burst-zoom.png`):
  - The board's +5 V (seen through U56's output high) ramps 30 → 44 ms.
  - At 45.77 ms: a 150 µs low (power-up glitch), then **51 short /OE pulses (240–280 ns, i.e. real ROM reads) between 46.01 and 47.53 ms**, irregularly spaced (median 18.7 µs, 0.9–238 µs). **After 47.5 ms, no ROM read ever again.**
  - **Meaning: the CPU starts and fetches from the boot ROM, but leaves it within ~1.5 ms.** Correct execution would read the ROM continuously: the first instructions are back-to-back fetches, then a 40 ms LDIR refetching `ED B0` every 6 µs. The first two reads are 2.8 µs apart, then there's a 52 µs gap. So the CPU goes astray after the first one or two instructions: **the bytes the CPU receives are not the bytes in the ROM** (data bus contention or a stuck bit, or a wrong/stuck ROM address line), or a video-RAM/WAIT interaction derails it.

**Data bus summary:** every line is frozen at a solid logic level: D7..D0 = 0 0 1 1 1 0 1 0 = **3Ah** (`LD A,(nn)`). The lows are hard lows (~0.16 V) with no blips during refresh cycles, so **something is driving a constant 3Ah onto the data bus all the time**. A constant value (not changing with PC/address) points to a **latch or stuck output enable** rather than a ROM or RAM. Prime suspect: **U76 i8212**, the video-data latch that drives the CPU data bus (enable DS1 = CS1, /DS0 = BNRD). Other candidates: the 8255 (U79) with stuck /CS·/RD, or the Z80 itself. The CPU then executes 3A 3A 3A… = LD A,(3A3Ah) forever, matching the "runaway" after ~1.5 ms.

Hypothesis: the CPU is **frozen mid-cycle**, e.g. stuck in a write with /WAIT held low by the video-RAM prioritiser U02, in which case the CPU itself drives the frozen data value 3Ah. Check /WR (22), /WAIT (24), /M1 (27).

**The CPU is frozen in the middle of a memory write**, with a running clock and no WAIT, BUSRQ or RESET asserted. A healthy Z80 cannot stop like this, because it only extends a write while /WAIT is low. The ROM reads in the power-up capture end ~1.5 ms after start, which is probably when it freezes. With the empty socket (step 4) the CPU ran continuously, so the freeze is tied to what the boot code does (it writes to video RAM at C000 within its first few instructions).

Hypotheses now:
1. **Faulty CPU** (MMN 80CPU) that hangs on some cycle/instruction.
2. **A WAIT glitch shorter than the probe sampling at the CPU pin.** Unlikely: the state is static for minutes.
3. **Clock problem only during certain cycles**, e.g. a clock-stretching mod. The clock was measured running while frozen, so unlikely.

**Next:** power-up capture of /M1 to see how long the CPU runs, then the diag02 (NOP) and diag01 (border) ROMs to see whether the CPU hangs even without RAM/video writes. Consider buying a spare Z80 (e.g. Zilog Z84C0006PEG CMOS or an NMOS Z8400A) for a swap test.

A properly reset Z80 always starts with an M1 fetch from 0000h.
- So the CPU is **not starting from a clean reset**. Strong new suspect: **the power-on reset circuit** (R09 2K2 / C15 10 µF electrolytic from ~1988 / D02). If C15 is dried out or open, /RESET rises together with VCC; the NMOS Z80 then wakes up in a random internal state and can hang. The K1 RESET button can't recover it, because it only acts during an M1 cycle. This would also explain why the empty-socket run happened to work: random start states. The 51 /OE pulses in the earlier capture remain unexplained (glitches or a partial run).

With the reset margins this tight (slow AT ramp, NRST = NPOR + 0.6 V), it is plausible.
- **Next test: AT28C16 "3 – FIX0"** (`boot80k_rf5_fix0.bin`, only byte 0 changed to `3E` = `LD A,83h`).

- **New prime suspect: U36 (7474) losing the startup map.** U36's first FF samples **BA7** on the **RFSH** edge (CLK = U36/3). R7 = 1 is constant, but during the preceding opcode fetch BA7 carries PC bit 7. When PC7 = 0 (all our ROM code sits at 0000–03FF), BA7 must rise 0→1 at the start of the refresh cycle **through the 7417 open-collector driver and its 620 Ω pull-up**, i.e. slowly. If U36 clocks before BA7 is high, PO latches 0 and the ROM disappears. This is the documented CoBra fault "**150 pF from U36/3 to GND**" (REV02: "press D, blue flash, freeze", LO6/PO falling). It's marginal and random: diag01 (tiny loop, no RAM traffic) ran for minutes, the RAM tests (heavy DRAM traffic) lose the map, and the boot crashes at random points. Other possibilities: LO6 glitch on U36/1 (/CLR1) or noise on NPOR (/PRE).
- **Not yet resolved:** whether the diag03 video-RAM FFh failure is a separate fault or a side effect. diag03 produced a coherent report, so the map was intact then.
